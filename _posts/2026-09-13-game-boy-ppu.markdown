## 背景：PPU 的概念、硬件瓶颈与架构演进史

### 1. 概念与历史定位：PPU 的本质及其与 GPU 的关系

### 硬件架构归类与 80 年代历史背景

在硬件架构归类上，Game Boy 的 PPU（Picture Processing Unit，图像处理单元） 属于 20 世纪 80–90 年代广泛使用的 2D 视频显示控制器（Video Display Controller, VDC） 或 视频显示处理器（Video Display Processor, VDP）。

20 世纪 70 年代末至 80 年代初，微型计算机与家用游戏机（如 Atari 2600）的 CPU 算力极度匮乏，无力承担逐像素的图像绘制。为了将 CPU 从繁重的图像刷屏工作中解放出来，半导体厂商开始设计独立于 CPU 运行的专用图形硬件。由于当时业内缺乏统一标准，不同半导体厂商与游戏巨头对其赋予了不同的工程称呼：

- **任天堂与理光（Nintendo / Ricoh 体系）：** 统称为 PPU（Picture Processing Unit）。理光（Ricoh）作为任天堂早期的核心半导体定制合作伙伴，为 FC/NES 设计了 RP2C02 芯片，首次将这一概念推向市场。随后该命名体系被延续至 Game Boy（DMG PPU）以及超级任天堂（S-PPU）。
- **世嘉与德州仪器（SEGA / Texas Instruments 体系）：** 统称为 VDP（Video Display Processor）。受早期德州仪器 TMS9918 架构的深远影响，世嘉（SEGA）在其 Master System 及 Mega Drive/Genesis 掌机与主机中，均将其专用图形芯片命名为 VDP。
- **通用半导体工业（NEC / MOS / 雅达利等）：** 普遍统称为 VDC（Video Display Controller） 或 CRTC（CRT Controller），如 NEC PC Engine 搭载的 HuC6270 VDC。

尽管称呼各异，这类芯片的物理本质均为基于固定功能管线（Fixed-Function）的硬件协处理器，专职负责根据 VRAM 中的图块索引表（Tile Map）与对象属性内存（OAM），在 LCD 或 CRT 的时钟同步脉冲下，实时合成 2D 图像信号。

### 客观厘清 PPU 与现代 GPU 的联系与界限

- **功能定位的前身：** PPU 是现代 GPU 的功能前身之一。它们核心的共同点在于“将图形渲染任务从通用 CPU 中剥离出来，交由专用硬件协处理器处理”。
- **架构机制的差异：** 现代 GPU 并非直接从 2D PPU 演变而来，而是起源于 90 年代中期的 3D 几何变换与光栅化加速卡。PPU 处理的是基于图块（Tile）和精灵（Sprite）的 2D 图块拼合；而现代 GPU 构建于 3D 多边形顶点流水线、像素着色器（Pixel Shader）和并行通用计算（GPGPU）之上。

### 2. 80 年代工程约束：为什么系统需要专门的 PPU 硬件？

在 1989 年 Game Boy 发布时，系统硬件设计面临两个不可逾越的物理瓶颈，这决定了必须依赖硬件级 PPU，而无法像现代软件渲染器那样采用全帧缓冲区（Off-screen Framebuffer）：

### ① 存储器介质限制与 BOM 杠杆（Memory Cost & BOM Multiplier）

**背景铺垫：为什么 1989 年的掌机显存必须选用 SRAM？** 在 1980 年代末，半导体存储器主要分为 DRAM（动态随机存取存储器） 与 SRAM（静态随机存取存储器）：

- **DRAM（1T1C 结构：1 晶体管 + 1 电容）：** 存储密度高、价格低廉，但靠电容容纳电荷存储数据，存在自然漏电，需要复杂的刷新电路且读写存在延迟/等待周期（Wait State）。对于电池供电、内部空间狭小且 PPU 必须在无等待周期（Zero-Wait State）下高速抓取图块的 Game Boy 而言，DRAM 无法胜任显存需求。
- **SRAM（6T 晶体管结构：6 晶体管双稳态锁存器）：** 只要通电就能稳定保持状态，读写速度极快且无需刷新电路，但缺点是结构复杂、占用芯片面积大、价格极其昂贵。为了保证 PPU 渲染管线流畅，Game Boy 的 VRAM（显存）必须全盘采用 SRAM。

Game Boy 屏幕分辨率为 160 x 144 像素。若采用全帧缓冲区方案，即使在 2bpp（4 级灰阶）下，单帧图像所需的裸位图数据量为：

单帧裸帧缓冲区大小 = (160 x 144 x 2 bits) / (8 bits/byte) = 5,760 Bytes 约合 5.625 KB

**1989 年真实半导体市场价格与 BOM 杠杆数据核算：**

- **SRAM 与 DRAM 价格悬殊：** 1988–1989 年间全球遭遇严重内存短缺，普通的 DRAM 市场单价高达约 200 至 500 美元 / MB。而 Game Boy 显存必须使用的 SRAM，每 MB 价格更是高达 1,500 至 2,500 美元 / MB（折合 1.5 至 2.5 美元 / KB）。
- **Game Boy 整机成本死线：** 1989 年 Game Boy 在北美发售价仅为 89.95 美元（日本首发价 12,500 日元）。消费电子行业普遍存在 3 至 4 倍的零售杠杆（零售价 = BOM 物料成本 x 3.5 至 4.0），这意味着整机 BOM（Bill of Materials）物料成本预算必须被极其严苛地控制在 22 至 25 美元左右。
- **连锁反应：** Game Boy 整机仅搭载了 8 KB 系统 WRAM（Work RAM，用于 CPU 通用计算与状态存储的工作内存）与 8 KB VRAM（Video RAM，用于 PPU 图像存储的显存），两者合计仅有 16 KB SRAM。如果为了支持 Framebuffer 而额外增加 16 KB 至 32 KB 高速 SRAM，仅新增内存的 BOM 采购成本就会增加 20 至 30 美元，导致零售价飙升至 160 至 180 美元。这不仅会让 Game Boy 失去性价比，还会直接被后来的竞品如 Sega Game Gear（1990 年发售价 149.99 美元）和 Atari Lynx（1989 年发售价 179.99 美元）在价格上绝杀。

### ② CPU 算力瓶颈与指令周期推论

Game Boy 的主 CPU（SM83）主频为 4.194304 MHz，内部 4 个振荡周期（T-Cycle）构成 1 个机器周期（M-Cycle，即 CPU 执行 1 次基础读写/指令微步的时间），故 M-Cycle 主频仅为 1.048576 MHz。 按约 59.73 Hz 的帧率计算，CPU 在单帧时间内可用的总算力预算仅有：

单帧算力上限 = 4,194,304 T-Cycles/s / 59.7275 Frames/s = 70,224 T-Cycles (17,556 M-Cycles)

若没有 PPU 硬件，完全依靠 CPU 软件处理全屏 160 x 144 = 23,040 个像素，仅仅做最紧凑的内存搬运，单帧耗时就已超越 CPU 算力预算的 300%，CPU 将无暇处理任何游戏逻辑。 因此，硬件工程师必须将“将固定大小的图块（Tile）拼凑成画面”这一算法硬件化，硬编码为专用逻辑电路，即 PPU。CPU 仅需更新极小量的数据（如 Tile ID 和坐标索引），具体的像素提取、优先度仲裁与扫描线输出全部由 PPU 自动化完成。

### 3. Tile（图块）机制的设计哲学：8 x 8 网格的解法

在明确了硬件内存与算力的极限后，工程师提出了将图像拆分为 8 x 8 像素的 Tile（图块） 这一核心的图形复用与数据去重（Deduplication）思想。

### ① 几何级的数据压缩（图砖复用 Deduplication）

如果整张 256 x 256 像素的背景大图全部采用二进制像素数组（位图）存储，即使在 2bpp（4 级灰阶）下，单地图也需要占用：

(256 x 256 x 2 bits) / (8 bits/byte) = 16,384 Bytes = 16 KB

而 Game Boy 整个视频显存（VRAM）只有 8 KB，甚至装不下这一张背景大图。

采用 Tile 机制后，地图由 32 x 32 = 1,024 个网格构成。对于草地、房屋墙壁、海洋等大量重复的元素，PPU 在显存中只需保存 1 个 8 x 8 像素的草地 Tile 数据（仅 16 字节），随后在地图索引表中填入 1,024 个 1 字节的 Tile ID 即可。 此时，存储一张 256 x 256 大地图的总空间降为：

1,024 Bytes (地图网格表) + 16 Bytes (单 Tile Data) = 1,040 Bytes 约合 1.01 KB

数据存储需求直接降低了 93.6%。

### ② 核心解耦：Tile Map 与 Tile ID 的二级间接寻址与偏置计算详解

理解 Tile 机制的最核心钥匙，在于厘清 **Tile Map（地图表）** 与 **Tile Data（图块仓库）** 之间的二级间接寻址解耦逻辑：

1. **Tile Map 是纯粹的“指针数组/二维网格”：** Tile Map 在 VRAM 中占据 1 KB 空间（32 x 32 = 1024 个网格）。Tile Map 本身不包含任何像素颜色或位图数据，它仅仅是一个按照平面布局排列的一维连续字节数组（以行为主序 Row-Major 排布），其中每一个网格只存放 1 个字节的编号——**Tile ID**（例如 `0x42`）。整张地图在水平方向上固定由 **32 个 Tile** 组成。
2. **Tile Data 是独立的“图形元素仓库”：** 真正的 8 x 8 像素原始位图（每个 Tile 占 16 字节）统一保存在 VRAM 的 Tile Data 区（`0x8000–0x97FF`）。

**偏置计算公式与数值实例推导过程：** 当 PPU 在渲染虚拟画布上的某个像素坐标 (X, Y) 时，硬件需要经历以下步骤查找到真实的像素：

- **Step 1: 计算网格坐标。** 因为每个 Tile 的尺寸是 8 x 8 像素，所以要将像素坐标转换为网格坐标（即第几行第几列的 Tile），只需将坐标分别除以 8（在硬件上即按位右移 3 位）： col = X / 8, row = Y / 8
- **Step 2: 计算一维线性内存偏移量（offset）。** 因为 Tile Map 在 VRAM 中是按行顺次展开的单维数组，当前行前面已经完整跨过了 row 行（每行 32 个字节），再加上当前行内的第 col 列偏置，就得到了该 Tile 在 Tile Map 数组中的字节偏移量公式： offset = row * 32 + col = (Y / 8) * 32 + (X / 8)
- **Step 3: 数值实例验证（带入具体坐标）。** 假设当前计算的像素坐标经滚动偏移后：X = 16，Y = 24。

- 所在列索引：col = 16 / 8 = 2（落在第 2 列）
- 所在行索引：row = 24 / 8 = 3（落在第 3 行）
- 代入公式计算： offset = 3 * 32 + 2 = 96 + 2 = 98 这就是 offset = 98 的精确数学来源。通过这个计算出的偏移量 98，硬件可以直接去内存地址 TileMap_Base + 98 处读取到 1 字节的 Tile ID（例如 `0x45`），进而前往 Tile Data 仓库中获取真正的像素位图。

```
Tile 机制二级间接寻址链路
┌──────────────────────────┐     Step 1: 网格坐标计算     ┌───────────────────────────────────┐
│ 屏幕/地图坐标 (X, Y)     │ ─────────────────────────► │ Tile Map 网格偏置                 │
│ (例如 Map_X=16, Map_Y=24) │                            │ offset = (Y/8)*32 + (X/8) = 98    │
└──────────────────────────+                            └─────────────────┬─────────────────┘
                                                                          │
                                                                          │ Step 2: 查表取 ID
                                                                          ▼
┌──────────────────────────┐     Step 3: 计算像素偏置     ┌───────────────────────────────────┐
│ 16 字节 2bpp 原始像素    │ ◄───────────────────────── │ Tile Map[98] = Tile ID (如 0x45)  │
│ (Tile Data 对应地址)     │                            │ (纯索引编号，不含任何像素)         │
└────────────┬─────────────┘                            └───────────────────────────────────┘
             │ Step 4: 移位解包
             ▼
┌──────────────────────────┐
│ 推送至 PPU 像素处理管线   │
└──────────────────────────┘
```

这种“数据与拓扑结构分离”的设计，将 2D 游戏开发中的场景布局逻辑（Map）与美术资产（Tile）彻底解耦。

### ③ 8 位 CPU 架构与门电路逻辑友好（总线宽度、位移对齐与无除法器设计）

8 x 8 像素的设计并非偶然，而是深度契合了 Game Boy 搭载的 8 位 CPU（SM83） 的物理特性、寄存器宽度与硬件门电路逻辑：

- **8 位数据总线原生适配（1 行 = 1 字节）：** Game Boy 的 CPU 和 SRAM 数据总线宽度均为 8 bits（1 字节）。一个 8 x 8 像素 Tile 的每一行刚好是 8 个像素，在 2bpp 的单个 Bitplane（位平面）中，每行数据刚好对应 1 个字节（8 bits）。CPU 或 PPU 单次执行 8 位读写指令，就能精准抓取一行像素的单位平面位图，彻底避免了跨字节的移位拼接与多余指令开销。
- **8 位 CPU 寄存器与无除法器位移（8 = 2的3次方）：** Game Boy 的 8 位 CPU（SM83）内部没有硬件除法指令（如 DIV 往往需要几十个时钟周期或靠软件循环实现）。而 8 x 8 像素刚好对应二进制中的 2的3次方。当 PPU 或 CPU 在计算某个屏幕坐标 (X, Y) 落在第几个 Tile 网格时，硬件甚至不需要执行除法，直接利用 8 位寄存器执行极为廉价的按位右移 3 位（`X >> 3`, `Y >> 3`），极大节省了 80 年代的硅片晶体管面积。

### ④ 极低成本的场景滚动与局部动画

- **支线 A：场景滚动（硬件加法器与虚拟画布）：** 在 VRAM 的 Tile Map 中，存储的是一张 32 x 32 图块（即 256 x 256 像素）的完整地图，而 Game Boy 的 LCD 屏幕只是一个 160 x 144 像素的视口（Viewport）。当 PPU 绘制屏幕第 Y 行、第 X 列的像素时，其内部的硬件加法器会实时计算坐标偏置： Map_X = (X + SCX) % 256, Map_Y = (Y + SCY) % 256 CPU 只需要写入 1 个字节存入 `0xFF43`（SCX）或 `0xFF42`（SCY）寄存器（耗时仅 2 个 M-Cycles），PPU 硬件就会在下个时钟周期对全屏像素自动应用新的坐标加法，实现零 CPU 负担的全屏顺滑滚动。
- **支线 B：局部动画（Tile ID 引用广播）：** 依靠 Tile Map 只存 Tile ID 的解耦特性，对于水面流转、岩浆翻滚等局部动画，CPU 完全无需重绘 32 x 32 的地图网格。因为全屏所有水面区域可能都引用了同一个 Tile ID（例如 ID `0x45`），CPU 只需要更新 VRAM 中 ID `0x45` 所对应的 16 字节原始位图数据，下一帧全屏所有引用该 Tile 的区域就会瞬间同步播放动画。

## 一、Game Boy VRAM 显存架构与像素数据编码

### 1. VRAM 内存映射结构

Game Boy 的 VRAM 容量为 8 KB，物理地址空间映射在 `0x8000 – 0x9FFF`。它被严格划分为两个功能区：Tile Data（图块位图区） 与 Tile Maps（图块映射表区）。

```
VRAM 物理内存映射 (0x8000 - 0x9FFF, 共 8KB)
┌───────────────────────────┬──────────────┬──────────────────────────────────────────┐
│ 地址范围                   │ 大小          │ 功能用途                                 │
├───────────────────────────┼──────────────┼──────────────────────────────────────────┤
│ 0x8000 - 0x87FF           │ 2 KB (128)   │ Tile Block 0 (仅 OBJ 与 BG/Win 共用)     │
│ 0x8800 - 0x8FFF           │ 2 KB (128)   │ Tile Block 1 (BG/Win 与 OBJ 共享交叠区) │
│ 0x9000 - 0x97FF           │ 2 KB (128)   │ Tile Block 2 (仅 BG/Win 可用)            │
│ 0x9800 - 0x9BFF           │ 1 KB (32x32) │ Tile Map 0 (背景或窗口图块表 0)          │
│ 0x9C00 - 0x9FFF           │ 1 KB (32x32) │ Tile Map 1 (背景或窗口图块表 1)          │
└───────────────────────────┴──────────────┴──────────────────────────────────────────┘
```

### ① Tile Data（图块位图区：`0x8000 – 0x97FF`）

存放在此处的是纯粹的图像位图定义，共包含 384 个 8 x 8 像素的 Tile。PPU 寻址 Tile Data 存在两种模式（通过 LCDC 寄存器 Bit 4 切换）：

- **`0x8000`** **寻址模式（Unsigned Tile ID）：** 以 `0x8000` 为基地址，Tile ID 为 0 至 255 的无符号整数。主要用于 Sprites（OBJ）以及部分 BG。
- **`0x8800`** **寻址模式（Signed Tile ID）：** 以 `0x9000` 为基地址，Tile ID 为 -128 至 127 的有符号整数。专门用于 BG 和 Window，目的是方便快速共享位于 Block 1 (`0x8800–0x8FFF`) 的通用字符集。

### ② Tile Maps（图块映射表区：`0x9800 – 0x9FFF`）

包含两个 32 x 32 字节的网格阵列。网格里的每个字节存储的仅仅是一个 1 字节的 Tile ID 编号。LCDC 寄存器的 Bit 3 和 Bit 6 分别决定了背景（BG）和窗口（Window）当前使用 Map 0 还是 Map 1.

### ③ OAM (Object Attribute Memory, 对象属性内存：`0xFE00 – 0xFE9F`)

独立于 VRAM 之外的 160 字节专用 SRAM 区域，由 40 个固定结构的 4 字节条目（Entry）组成，专门用于存储每个 Sprite 的硬件控制与定位属性：

```
OAM 单个 Sprite 属性结构 (共 4 字节 / 32 bits)
┌──────────────┬────────────────────────────────────────────────────────┐
│ 字节偏移     │ 功能定义与底层硬件语义                                 │
├──────────────┼────────────────────────────────────────────────────────┤
│ Byte 0       │ Y 坐标 (屏幕 Y + 16)。决定精灵在垂直方向上的对齐位置。    │
├──────────────┼────────────────────────────────────────────────────────┤
│ Byte 1       │ X 坐标 (屏幕 X + 8)。决定精灵在水平方向上的对齐位置。    │
├──────────────┼────────────────────────────────────────────────────────┤
│ Byte 2       │ Tile Index (图块索引)。指向 VRAM 中对应图形位图的编号。  │
├──────────────┼────────────────────────────────────────────────────────┤
│ Byte 3       │ Flags (控制标志位)：                                   │
│              │ - Bit 7: BG-to-OBJ Priority (背景与精灵遮挡优先级)     │
│              │ - Bit 6: Y-Flip (Y 轴垂直翻转)                         │
│              │ - Bit 5: X-Flip (X 轴水平翻转)                         │
│              │ - Bit 4: Palette Number (调色板选择 OBP0 / OBP1)       │
│              │ - Bit 3-0: 兼容性保留/扩展位 (DMG 模式下恒为 0)          │
└──────────────┴────────────────────────────────────────────────────────┘
```

**工程深挖：为什么这 160 字节必须做成独立的片上 SRAM？** OAM 的容量极其微小（共 40 个 Sprite，总计 160 字节），连系统总内存的 1% 都不到。但硬件工程师必须将其设计为独立片上 SRAM，核心逻辑在于：

- **超高时序要求：** 在每条扫描线开头的 Mode 2 阶段，PPU 必须在短短 80 T-Cycles 内把 40 个精灵的坐标全部比对一遍，找出当前行要绘制的最多 10 个精灵。
- **避免总线死锁（Bus Contention）：** 如果把 OAM 混放在 VRAM 里面，PPU 扫描 OAM 时就会死锁 VRAM 数据总线，导致无法并行抓取背景 Tile 数据。 因此，硬件工程师是用极微小的 SRAM 成本，换取了不占用 VRAM 带宽的独立硬件双通道极速扫描能力。

### 2. 2bpp (2 Bits Per Pixel) & 位平面 (Bitplane) 编码机制

Game Boy 屏幕支持 4 级灰阶，对应 2 位色彩索引（Color ID: 0b00 到 0b11）。每个 8 x 8 像素的 Tile 刚好需要：

8 x 8 x 2 bits = 128 bits = 16 Bytes

PPU 在存储这 16 个字节时，采用了位平面交错格式（Interleaved Bitplane Format）。Tile 中的每一行（8 个像素）由 2 个字节表达：

- **Low Byte（低位字节）：** 存储这 8 个像素 Color ID 的 Bit 0。
- **High Byte（高位字节）：** 存储这 8 个像素 Color ID 的 Bit 1。

针对一行中从左到右第 n 个像素（0 <= n <= 7，最高位 bit 7 对应最左侧像素 n=0）：

Color ID[n] = (((High Byte >> (7 - n)) & 1) << 1) | ((Low Byte >> (7 - n)) & 1)

## 二、PPU 状态机与 Pixel FIFO 硬件管线

### 1. PPU Mode 状态机工作流与 H-Blank/V-Blank 历史演进

Game Boy LCD 硬件的显示刷新过程在时间轴上被切分为 154 行扫描线（Line 0 至 153），其中 Line 0 至 143 为可见渲染行，Line 144 至 153 为垂直空白期（V-Blank）。渲染一行完整的扫描线需要 456 个 T-Cycles。PPU 内部基于一个 4 模式状态机（Mode 0 到 3）运行：

```
单条扫描线 (Line 0 - 143) 周期 (456 T-Cycles)
┌──────────────────────────────┬──────────────────────────────────────────────┬───────────────────────────────┐
│ Mode 2: OAM Search           │ Mode 3: Pixel Transfer                       │ Mode 0: H-Blank               │
│ (80 T-Cycles)                │ (172 - 289 T-Cycles)                         │ (87 - 204 T-Cycles)           │
│ CPU 无法访问 OAM             │ CPU 无法访问 VRAM / OAM / Palette            │ CPU 可自由访问 VRAM 与 OAM    │
└──────────────────────────────┴──────────────────────────────────────────────┴───────────────────────────────┘
                          一整帧 (Line 0 - 153) 渲染时间轴
Line 0 - 143  : [ Mode 2 -> Mode 3 -> Mode 0 ] 循环执行 144 行
Line 144 - 153: [ Mode 1: V-Blank ] 持续 4560 T-Cycles，触发 V-Blank 中断 (INT 0x40)
```

- **历史与工程意义：** H-Blank（Mode 0）与 V-Blank（Mode 1）继承自 CRT 显示器的电子枪回扫期。由于 PPU 在 Mode 3 活跃渲染阶段会封锁 CPU 对 VRAM/OAM 的访问总线，因此空白期是 CPU 安全更新显存与精灵属性的唯一硬件安全窗口。

### 2. 真实硬件 Pixel FIFO（先入先出像素队列）渲染管线

- **Pixel FIFO 的定义与作用：** FIFO 是一种硬件数据缓冲结构。在 Game Boy PPU 内部，**Pixel FIFO** 是一个位于 PPU Mode 3 渲染流水线末端、容量为 8 到 16 个像素的片上硬件移位缓冲队列。
- **解耦抓取与显示节拍：** 前端的 Fetcher（抓取器）从 VRAM 批量抓取图块并解包为像素推入 FIFO 尾部；LCD 驱动电路在后段每周期从 FIFO 头部弹出 1 个像素送显。当屏幕滚动或遇到 Sprite 覆盖时，Fetcher 会暂停背景抓取，而 LCD 驱动电路依旧在稳定消费像素，这正是 Mode 3 耗时会动态波动的底层原因。

## 三、完整一帧渲染全流程与像素级仲裁推导

**概念定义：什么是像素仲裁（Pixel Arbitration）？** 当背景（BG）、窗口（Window）与多个精灵（Sprite）重叠在同一个屏幕坐标 (X, Y) 时，PPU 硬件依据特定规则（如 Color 0 透明色、OAM 优先级标志等）在 1 个时钟周期内实时计算并判定到底由哪个图层的像素遮挡其他图层、并输出到 LCD 屏幕的决策过程。

下面以经典关卡画面为例，推导一帧内 154 行扫描线的时空流转与像素仲裁。

### 1. 关卡画面帧物理构图布局

- **背景层（BG Layer）：** 天空云朵与山丘背景（位于 Map 0 `0x9800`）。
- **活动块（Sprites Layer）：** 主角站在 Y = 88 行的地面草地位置。
- **窗口层（Window Layer）：** 屏幕底部 Y >= 120 区域强行覆盖了用于显示分数与生命值的 HUD 对话框。

寄存器典型配置：`LCDC = 0xB3`, `SCX = 0`, `SCY = 0`, `WY = 120`, `WX = 7`, `BGP = 0xE4`。

### 2. 逐行渲染全时间轴推演 (Line 0 至 153)

- **Line 0 至 87（顶部纯背景行）：** 纯粹根据背景地图抓取天空云朵与远山。
- **Line 88 至 103（精灵与草丛覆盖区）：** OAM 扫描匹配到精灵，解包 2bpp 数据，跳过透明色，将精灵轮廓与草地背景按优先级合并。
- **Line 104 至 119（地下泥土背景区）：** 绘制地表下方的斑点泥土纹理。
- **Line 120 至 143（底部 HUD 菜单窗口区）：** 满足 LY >= WY 触发条件，PPU 强制切换为 Window 坐标，渲染底部 UI 菜单，背景地图被完全覆盖截断。
- **Line 144 至 153（V-Blank 阶段）：** 进入 Mode 1，触发 V-Blank 中断，CPU 在此期间更新游戏逻辑与显存状态。

### 3. 单个像素点三层叠加仲裁推导

假设在 Line 125、X 坐标 30 的位置（位于底部 HUD 菜单区域）：

1. **Window 判定：** 满足 WY = 120 且 Line = 125，Window 层激活，输出颜色编号为 3（黑色文本）。
2. **Sprite 判定：** 若此处有精灵重叠且设置了背景优先（Priority = 1）。
3. **仲裁计算：** 由于 Window 像素颜色索引 3 不等于 0，且精灵设置了背景优先，PPU 判定精灵像素被遮挡，最终保留 Window 的黑色文本像素，通过调色板映射后输出至 LCD 屏幕。

## 四、总结与架构对比

| 维度 | 传统全帧缓冲区架构 (Framebuffer) | Game Boy PPU 扫描线/Tile 架构 |
| --- | --- | --- |
| 显存依赖 | 需要完整 Framebuffer（5.6KB+ SRAM） | 仅需要 VRAM Tile 表与 160B OAM |
| 渲染逻辑 | CPU/GPU 逐像素写内存 Framebuffer | PPU 硬件管线随 LCD 时钟实时输出 |
| 动画/滚动开销 | 高（全屏像素重新绘制写显存） | 极低（仅改 SCX/SCY 或单 Tile Data） |
| 硬件成本与功耗 | 极高（1989 年 SRAM 昂贵且功耗大） | 极低（硬编码逻辑电路，零冗余内存） |

通过硬件级专用管线与 Tile 机制的设计，Game Boy PPU 在 1989 年极其匮乏的 SRAM 与 CPU 算力限制下，实现了高效、低功耗的 2D 图形实时合成，其针对片外存储带宽与计算开销的优化思想至今仍深刻影响着现代移动图形架构。
